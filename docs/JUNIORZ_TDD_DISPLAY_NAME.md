# תרגיל 2 – ולידציה בצד השרת (TDD)

## מה הייתה הבעיה?
במשחק **Sababich** בדקנו ב־Unity ששם התצוגה (`displayName`) אינו ריק. אבל אפשר לעקוף את המשחק ולשלוח בקשת API ישירה ל־Cloud Save, ולכן בדיקה בצד הלקוח אינה מספיקה.

## מה עשינו? RED → GREEN

**1. RED – כתבנו טסט לפני התיקון**  
שלחנו ל־Default Cloud Save שם שמכיל רווחים בלבד (`"   "`). ציפינו לדחייה, אבל השרת החזיר `HTTP 200` ושמר את הערך. הטסט נכשל והוכיח שהבדיקה ניתנת לעקיפה.

**2. תיקון בשרת**  
יצרנו סקריפט `SetDisplayName` ב־**Unity Cloud Code**. הוא בודק את השם בשרת, דוחה שם ריק או רווחים בלבד, ושומר שם תקין ב־**Protected Player Data**.

**3. חיבור המשחק**  
עדכנו את `ScoreOfAuthenticatedUser.cs` כך שהמשחק שולח את השם ל־Cloud Code במקום לשמור אותו ישירות ב־Default Cloud Save. אם הבדיקה נכשלת, המשחק לא ממשיך לסצנה הבאה. שאר נתוני ההתקדמות ממשיכים להישמר כרגיל.

**4. GREEN – הרצנו שוב בדיקות**  
שלושת הטסטים החדשים עברו. בדקנו גם הרשמה תקינה מתוך Unity, וגם מצב שבו שלחנו בכוונה שם לא תקין והמשחק עצר את תהליך הכניסה.

## מהלך הטסט

| מה שלחנו | מה ציפינו | מה קרה בפועל |
|---|---|---|
| `"   "` ישירות ל־Cloud Code | דחיית שם לא תקין | `422 – INVALID_DISPLAY_NAME` |
| `"JuniorZ Tester"` ל־Cloud Code | שמירה תקינה | `200`, והשם נקרא בחזרה מ־Protected Data |
| ניסיון לשנות ישירות את השם המוגן באמצעות טוקן של שחקן | שהשינוי לא יתבצע | `401`, ובקריאה חוזרת השם נשאר `"JuniorZ Tester"` |

**למה קיבלנו 401 ולא 403?**  
`401` פירושו שהשרת לא קיבל את הטוקן לצורך הפעולה. `403` פירושו שהטוקן התקבל, אבל אין הרשאה לבצע אותה. בבדיקה שלנו טוקן של שחקן לא התקבל עבור כתיבה ישירה ל־Protected Data, ולכן קיבלנו `401`. בדקנו לאחר מכן שהשם לא השתנה. כלומר, **הוכחנו שניסיון העקיפה שנבדק נכשל**, ולא שהשרת הגיע לשלב בדיקת ההרשאות של `403`.
